# Мониторинг интеграций

Сервис наблюдения за синтетическими событиями интеграций. 

## Обзор интеграций

На `/overview` доступны четыре KPI (всего, успешно, с ошибкой, доля ошибок), три диаграммы Recharts и последние пять ошибок с причиной и подробностями. Все значения поступают из SQLite через `/api/overview`; временной ряд строится по времени события в UTC, пустые интервалы заполнены нулями. Источники представлены как top 10 и сумма «Остальные», без повторного учёта. При пустой выборке доля ошибок — «—», графики заменяются пояснением.

Клик по столбцу времени задаёт точный диапазон `[from,to)`, клик по источнику или сектору статуса применяет соответствующий фильтр. Поиск, статус, несколько источников/типов и период работают вместе. Для диаграмм источников и статусов есть таблицы с точными значениями и кнопками для работы с клавиатуры; полные названия и доли источников доступны в таблице и tooltip. «Остальные» — агрегат, конкретный источник выбирается через фильтры. Границы периода сохраняют миллисекунды, включая интервалы с единственным событием.

Вкладки «Обзор / События» сохраняют условия и уже загруженный срез, в том числе после ручного обновления. Используются общие query и первые 50 событий; весь журнал в браузер не загружается. Recharts загружается отдельно при открытии обзора. Диаграммы адаптивны, используют цвета обеих тем; анимации данных отключены, включая режим reduced motion. При смене условий предыдущий обзор остаётся виден с уведомлением, его действия временно недоступны.

## Журнал событий

Откройте `/events`. Поиск работает по словам и началу слова (русский и английский), применяется через 300 ms или Enter. Статус, несколько источников, несколько типов и UTC-период сочетаются; сортировка по поступлению, времени события, источнику, типу или статусу выполняется сервером для всей выборки. Фильтры на узком экране применяются одной кнопкой; отмена сохраняет прежние условия. Конец временного интервала не включается.

Условия и выбранный ID хранятся в URL (`event` содержит исходный ID с URL-кодированием); ссылка на подробности работает после обновления страницы и вне текущей выборки. API-путь ID использует отдельный `eventSlug`. Подробности показывают оба времени, полный текст, код ошибки и payload; копирование требует разрешённого Clipboard API (HTTPS или loopback). При отказе показана ошибка, текст доступен для ручного выделения.

При смене условий TanStack Query сохраняет предыдущую согласованную выборку до готовности новой; загрузка обозначена тонкой полосой, ошибка не очищает список. Порции по 50 записей, максимум 20 порций в текущем окне. Есть кнопки загрузки в обе стороны и автоматическая догрузка у края; DOM виртуализован. Старые неактивные выборки ограничены двумя, facets — четырьмя, детали — восемью; GC неактивных журналов — 10 минут, остальных query — 60 с. Последняя выборка (до 100 строк и 200 000 символов JSON) сохраняется на 10 минут в sessionStorage текущей вкладки; payload не сохраняется. Ошибочный кеш отбрасывается. Back/Forward восстанавливает сохранённый якорь, пока срез и кеш доступны. При утрате кеша/смене поколения открывается новый срез с уведомлением; после refresh старый пиксельный скролл не обещается.

Вход не требуется: журнал и API доступны без учётных записей, cookie-сессий и API-ключей. Одна иконка переключает темы по циклу системная → светлая → тёмная; выбор сохраняется между посещениями.


## Запуск

Нужны Node.js **24.21.0**, npm **11.19.0**. Версии записаны в `.nvmrc`, `.node-version`, `package.json`; другая major-версия Node отвергается. Для сборки `better-sqlite3` могут потребоваться Python 3, make и C++ compiler (на macOS — Command Line Tools).

```bash
nvm use
npm ci
cp .env.example .env.local
npm run db:migrate
npm run db:seed
npm run dev
```

Открыть [http://127.0.0.1:3000](http://127.0.0.1:3000). Команда dev использует webpack, как и production build. Для проверки production:

```bash
npm run build
npm start
```

`build` создаёт standalone-вывод и добавляет в него static/public assets. `start` запускает именно standalone server. Сборка не требует `.env`, действующей БД или секретов. Запуск валидирует конфигурацию **до открытия порта**. Неподдерживаемые дополнительные CLI-аргументы для host/port не используются; настройки задаются через env.

## Конфигурация

`.env.example` задаёт `HOST=127.0.0.1` и `PORT=3000`. Для доступа с другого устройства можно задать `HOST=0.0.0.0`. Профили доступа, HTTPS origin и секреты не нужны.

`DATABASE_PATH` — абсолютный путь к `.db`, `.sqlite` или `.sqlite3`. По умолчанию локально это `<корень проекта>/data/events.db`, в контейнере `/app/data/events.db`. Пути внутрь `public`, `.next`, `out`, включая существующие symlink, отвергаются. Сам валидатор ничего не создаёт. `db:migrate` явно создаёт каталог и БД; runtime-accessor лениво открывает только существующую актуальную схему. При открытии проверяются SQLite ≥3.51.3, FTS5, WAL, `synchronous=FULL`, `foreign_keys=ON`, `busy_timeout=1000`. Фактически проверен движок 3.53.4. Ошибки конфигурации не печатают значения секретов.

После обновления выполните `npm run db:migrate`: новая миграция удаляет таблицы пользователей, сессий и учётных данных. События сохраняются; старые миграции не переписываются.

## HTTP API

Контракт: [OpenAPI 3.1](docs/api/openapi.json), точная семантика — [архитектурные контракты](docs/plans/01-architecture-contracts.md#5-общий-контракт-http). Все ответы запрещают кеширование через `Cache-Control: no-store` (потоки также `no-transform`) и имеют `X-Request-ID`; ошибка — `{error:{code,message,fields?,request_id}}`, её код также доступен в `X-Error-Code`.

| Маршрут                                 | Результат                                                                                           |
| --------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `GET /api/events`                       | `{items,page,snapshot}`, первая полезная страница без предварительного overview                     |
| `POST /api/events`                      | `{event,replayed}`, 201 новая запись / 200 повтор / 409 другой объект с тем же ID                   |
| `GET /api/events/~<base64url UTF-8 id>` | `{event}` с полным payload; ID в DTO исходный                                                       |
| `GET /api/overview`                     | Счётчики, доля ошибок, заполненный нулями UTC-ряд, top 10 источников + other, пять последних ошибок |
| `GET /api/facets?field=source`          | Значения/счётчики справочника, selected включая нулевые; также `field=type`                         |
| `GET /api/events/export?format=csv`     | Поток CSV/JSON всей выборки; `HEAD` для проверки и count, максимум 100 000 событий                  |

По умолчанию API и журнал показывают события **за всё время**. В этом режиме `snapshot.from` и `snapshot.to` равны `null`; даты событий, в том числе старые и будущие, не ограничиваются. Пагинация сохраняется. В интерфейсе выбран пункт «За всё время».

Фильтры: `status=success|error`, повторяемые `source`/`type` (OR внутри, AND между категориями), Unicode prefix-поиск `q`, `preset=24h|7d|30d` (только при явном выборе) либо пара RFC3339 `from`/`to` (UTC `[from,to)`, ≤366 дней). Сортировка `sort=seq|created_at|source|type|status`, `direction=asc|desc`; default seq DESC. Порция `limit=1..100`, default 50. У текста source/type NFKC/lowercase BINARY порядок, затем seq в том же направлении. Пустые/неизвестные параметры, повтор скалярного параметра и недопустимый поиск отвергаются с 400.

Первый ответ фиксирует `snapshot.token`. Передайте его другим endpoints, чтобы список, KPI и графики читали одни фильтры/UTC-границы и `seq <= max_seq`. `cursor` один наследует snapshot, sort, direction и limit; явно повторённые значения должны совпасть. `next_cursor`/`previous_cursor` не используют OFFSET. Новые вставки не меняют открытый срез. После restore другого поколения — 409 `SNAPSHOT_STALE`; watermark впереди истории — `SNAPSHOT_AHEAD`. Получите новый snapshot, не смешивайте ответы. Ключ подписи курсоров автоматически хранится в БД и не связан с доступом пользователей. Facets исключают из общего предиката только собственную категорию; `facet-q` ищет буквальный нормализованный префикс, limit default 100/max200, курсор отдельного домена.

### Повторяемая демонстрация POST

После настройки env, миграций и запуска сервера:

```bash
curl -i http://127.0.0.1:3000/api/events \
  -H 'Content-Type: application/json' \
  --data '{"id":"evt-http-demo-1","source":"amoCRM","type":"lead.created","status":"success","created_at":"2026-11-07T12:15:00Z","message":"Тестовая заявка передана"}'

curl -i http://127.0.0.1:3000/api/events \
  -H 'Content-Type: application/json' \
  --data '{"id":"invalid-demo","status":"pending"}'

curl 'http://127.0.0.1:3000/api/events?from=2026-11-07T00:00:00Z&to=2026-11-08T00:00:00Z'
```

Первый запрос — 201, повтор — 200 без новой записи; второй — 400 `VALIDATION_ERROR` без вставки. Явный диапазон в GET находит демонстрацию независимо от текущего дня. Все шесть базовых полей обязательны; неизвестные поля, null, массив вместо объекта, неверные даты/типы и пустые строки отвергаются. Тело ≤64 KiB UTF-8 JSON, payload-объект ≤16 KiB/depth16; compressed body не принимается. Путь деталей можно построить браузерным `eventSlug` из `src/shared/events.ts`.

## Хранилище и обслуживание

```bash
npm run db:migrate      # создать БД / применить только новые миграции
npm run db:seed         # добавить 360 синтетических событий, без удаления истории
npm run db:check        # schema/checksums, integrity, foreign keys, FTS/content
npm run db:rebuild-fts  # перестроить только поисковый индекс
npm run db:benchmark    # 100 000 событий в НОВОЙ временной БД и EXPLAIN-отчёт
```

Команды читают `DATABASE_PATH` из shell / `.env.local`; без него используют `data/events.db`. Они не требуют HTTP-сервера или настройки доступа. Миграции выполняйте до приёма трафика, одним процессом. Schema push/reset и автоматического seed нет. Checksums применённых SQL проверяются: старые миграции нельзя переписывать. `db:generate -- --name=...` создаёт новую миграцию; STRICT/FTS/триггеры нужно отдельно проверить в SQL, поскольку Drizzle Kit не описывает их полностью.

Demo-seed охватывает 30 суток: пять источников, четыре типа, оба статуса, всплеск ошибок, пустые дни, длинные сообщения, коды причин и безопасные payload. Дата основания сохраняется при первом запуске; повторная команда даже в другой день не добавляет дублей и не передвигает историю. Для обновления демонстрационного периода используйте отдельную новую БД. Малый детерминированный набор для тестов содержит 12 записей. Benchmark печатает путь к временной БД и оставляет её для анализа; рабочую БД он не использует.

События append-only. Вставка и FTS обновляются атомарно; одинаковый нормализованный ID/объект возвращает существующую запись, конфликт данных отвергается. Запрет UPDATE/DELETE/REPLACE действует в БД. Поиск индексирует ID, источник, тип и сообщение: Unicode61, префиксы слов, AND между токенами, русский/английский без учёта регистра. Пользовательский MATCH-синтаксис преобразуется в литеральные токены; предел — 200 символов / 10 токенов. Морфология, подстрока внутри слова и поиск по payload не реализованы.

### Резервное копирование и восстановление

```bash
npm run db:backup -- "$PWD/backups/events-20261107.db"
npm run db:restore -- "$PWD/backups/events-20261107.db" "$PWD/data/restored-20261107.db"
DATABASE_PATH="$PWD/data/restored-20261107.db" npm run db:check
```

Каждый раз выбирайте новый абсолютный путь с расширением `.db`, `.sqlite` или `.sqlite3`. Существующий файл, symlink и sidecar назначения приводят к отказу. Backup использует Online Backup API и допускает работающий WAL; простое копирование одного `.db` не подходит. Копия проверяется во временном закрытом каталоге, checkpoint выполняется до публикации; непроверенный файл не становится результатом. Исходная БД не удаляется/не заменяется. Копии имеют права 0600.

Restore поддерживает копии с текущей версией миграций: проверяет схему, SQLite/foreign keys и соответствие FTS основным данным, меняет `history_id` и удаляет восстановленные сессии. Обычный рестарт сохраняет поколение. После проверки восстановленной БД остановите приложение, задайте новый `DATABASE_PATH` и запускайте его; исходную БД и backup сохраните. Для старой версии копии используйте совместимую версию приложения и отдельную процедуру обновления. Автоматического переключения рабочей БД и разрушительного rollback нет.

В production CLI находится в том же образе:

```bash
docker compose run --rm --no-deps app node scripts/db.ts migrate
docker compose run --rm --no-deps app node scripts/db.ts check
```

Имя сервиса см. в `compose.yaml`. Backup/restore через контейнер требуют назначения на смонтированном постоянном диске. План хранения: 7 дневных и 4 недельных копии вне рабочего volume; расписание и внешнее хранилище настраивает владелец на этапе эксплуатации. Копия на том же диске не защищает от потери сервера.

## Realtime и демонстрационный поток

Новые данные поступают автоматически; рядом с заголовком показан компактный индикатор Live. Журнал у начала списка обновляется при любой выбранной сортировке, обзор — автоматически вместе с графиками. Близкие уведомления объединяются каждые 200 мс; счётчики не прибавляются на клиенте. Во время просмотра истории, подробностей и при фокусе на строке срез сохраняется, чтобы не переставлять строки под курсором. Возврат к началу журнала автоматически применяет новые данные. Кнопок паузы/ручного обновления, технических статусов транспорта и баннера поступлений нет.

`GET /api/events/stream?after=<history_id>:<max_seq>` читает commit из SQLite порциями по seq; память процесса не служит журналом изменений. Автопереподключение EventSource использует Last-Event-ID (приоритет над after). Тип `events.changed`, ID `history_id:seq`, data `{history_id,max_seq,count}`; ready/heartbeat дополнительно сообщают `heartbeat_ms`. Поколение не совпадает, курсор впереди БД или backlog слишком велик — `resync` и новый snapshot. Рестарт сохраняет историю; restore меняет поколение. Дубликаты уведомлений игнорируются. Поток не фильтруется и не передаёт payload.

По умолчанию: чтение БД каждые 500 мс, heartbeat 15 с, 32 соединения, batch 100, catch-up до 10 000 записей; очередь не более одного кадра. Медленный читатель отключается после двух heartbeat-интервалов. Abort/закрытие вкладки освобождают таймер и слот. При лимите сервер возвращает 503 / STREAM_LIMIT / Retry-After: 5. Если SSE не восстанавливается, клиент каждые 10 с проверяет watermark через GET; просмотр истории остаётся фиксированным. Возвращение SSE отключает polling. Транспортные состояния в UI не выводятся. Ошибки сети оставляют последний согласованный набор.

Генератор запускается только вручную и отправляет обычные POST, без прямой записи в БД:

```bash
npm run demo -- --url http://127.0.0.1:3000 --count 20 --interval-ms 1000
# Каждое пятое событие — ошибка, каждое седьмое — запоздавшее на сутки.
npm run demo -- --count 50 --interval-ms 200 --error-every 3 --late-every 7 --replay-every 4
npm run demo -- --help
```

Ctrl+C / SIGTERM прерывают ожидание и незавершённый запрос; уже подтверждённые события остаются в БД. Генератор не выполняет автоматические повторы после неоднозначной сетевой ошибки. Он печатает уникальный ID запуска и число подтверждённых сервером событий. count ограничен 1–10 000, interval-ms — 100–60 000; `--error-every 0` и `--late-every 0` отключают соответствующие сценарии. `--replay-every N` дополнительно повторяет каждый N-й POST с тем же ID/содержимым и проверяет `replayed`; `count` остаётся числом уникальных событий.

Для proxy нужно сохранить поток: отключить buffering/cache для `/api/events/stream` (например, nginx `proxy_buffering off; proxy_cache off; proxy_read_timeout 75s;`). Сервер отправляет `X-Accel-Buffering: no` и `Cache-Control: no-store, no-transform`. Проверка реального production proxy относится к этапам 10–11; p95 ≤2 с пока не заявляется измеренной характеристикой.

## Экспорт CSV и JSON

Кнопка «Экспорт» доступна в обзоре и журнале. Диалог фиксирует текущий срез, показывает полное количество совпадений и сортировку; в файл попадают все совпадения, включая ещё не загруженные страницы. Формат и срез сохраняются до закрытия диалога. Скачивание идёт средствами браузера; ход загрузки и отмена — в его разделе загрузок. Сообщение в приложении означает передачу скачивания браузеру, а не подтверждение сохранения файла.

`GET /api/events/export?format=csv|json` принимает общие фильтры (`status/source/type/q/preset/from/to`), `snapshot`, `sort` и `direction`. Для выгрузки именно экранной выборки передавайте её `snapshot` из overview/list и текущий порядок. Без snapshot сервер фиксирует новый срез. `limit/cursor` недопустимы. `HEAD` с теми же параметрами проверяет выборку и возвращает `X-Export-Count` без потока. Пример отдельной выгрузки ошибок за всё время:

```bash
curl --fail --output events.json 'http://127.0.0.1:3000/api/events/export?format=json&status=error&sort=seq&direction=desc'
```

JSON содержит `snapshot`, нормализованные `filters`, `sort`, `direction`, `count` и `items` со всеми полями событий, включая полный payload. CSV: UTF-8 с BOM, запятая, CRLF; стабильные столбцы `id,source,type,status,created_at,message,seq,received_at,error_code,payload`. Все ячейки заключены в кавычки, внутренние кавычки удваиваются; переносы сохраняются. Payload записывается как JSON в ячейке. Перед текстом с префиксом `=`, `+`, `-`, `@` (в том числе после пробельных/управляющих символов), а также начальной табуляцией/CR/LF добавляется апостроф для защиты от формул. Это намеренное преобразование CSV; JSON сохраняет исходный текст. Пустой CSV содержит заголовок, пустой JSON — `count: 0` и `items: []`.

Лимит — 100 000 записей за файл; превышение даёт 413 / `EXPORT_LIMIT` до заголовков вложения и тела. Уточните период/фильтры. До двух активных выгрузок, 20 запросов в минуту вместе с HEAD; превышение — 429 с `Retry-After`. Дедлайн потока — 5 минут. Сервер читает по 100 записей, уступает event loop между порциями, учитывает backpressure и освобождает слот при завершении/отмене. Новые вставки не меняют срез. Ошибка до начала тела возвращается в обычном формате; `X-Error-Code` доступен и в HEAD. Прерванный после начала ответа файл считается незавершённым: проверьте статус загрузки и повторите её. Долгая SQLite-транзакция во время скачивания не удерживается. Проверка задержек ingest и RSS при production-нагрузке остаётся этапу 11.

## Проверки

```bash
npm run check
npm run test:http  # после build, который входит в check
npx --no-install playwright install chromium firefox webkit
npm run test:e2e
```

`check` запускает форматирование в режиме проверки, ESLint без warnings, генерацию Next-типов/TypeScript, Vitest и production build. Unit-тесты проверяют конфигурацию и native SQLite. Интеграционные тесты используют отдельные временные файловые БД: ограничения, миграции, seed, нормализацию, конкурентные повторы из отдельных процессов, rollback/FTS, занятый writer, сохранность WAL после аварийного выхода процесса, backup/restore и SQL keyset в обоих направлениях. Дополнительно проверяются API-контракты, HMAC tokens, все сортировки/курсоры, фильтры/агрегаты/facets, идемпотентность, ошибки/лимиты, открытый API и отсутствие периода по умолчанию. `test:http` копирует standalone в отдельный временный каталог и проверяет настоящий production HTTP: конкурентные доставки, страницы, snapshot и сохранение истории после рестарта процесса. Рабочая БД в тестах не открывается. Существующий Playwright-набор рассчитан на production server в Chromium, Firefox и WebKit: темы/перезагрузку/системный режим/вкладки, применение темы до hydration, клавиатуру, axe, 320 px и desktop, отсутствие статических data/env routes. Прогоны Playwright выполняются только по явному поручению пользователя; в этапе 06 они не запускались.

Отдельные команды: `npm run lint`, `npm run typecheck`, `npm test`, `npm run test:watch`, `npm run format:check`, `npm run format`. Трейсы при сбое и скриншоты сохраняются в игнорируемом `test-results/`.

GitHub Actions выполняет те же проверки и браузеры на Linux; отдельная ARM64 job собирает и запускает Docker non-root. Удалённый запуск workflow требует размещения репозитория на GitHub и этим этапом не подтверждён.

## Контейнер

```bash
docker build -t integration-monitor:local .
```

Образ использует закреплённый Node 24 Debian slim и multi-stage: toolchain остаётся в builder, standalone runtime работает от `node`. Из build context исключены `.env*`, SQLite/WAL/SHM, backup, ключи и локальные артефакты. База не создаётся при build/start. Standalone и Docker включают CLI обслуживания и SQL-миграции.

Для локального smoke без сети контейнера:

```bash
docker run --rm --name monitor-scaffold \
  -e HOST=127.0.0.1 \
  integration-monitor:local
```

В другом терминале:

```bash
docker exec monitor-scaffold node -e "fetch('http://127.0.0.1:3000').then(r=>console.log(r.status))"
```

В этом примере сервер слушает loopback внутри контейнера. `compose.yaml` задаёт `HOST=0.0.0.0`, port mapping хоста и именованный volume без дополнительных секретов. Перед запуском приложения примените миграции через `docker compose run --rm app node scripts/db.ts migrate`, затем seed при необходимости. Автоматического применения схемы при старте нет.

## Стек и структура

Next.js 16.4.5 / React 19.3.1 / TypeScript strict; Tailwind CSS 4, next-themes, TanStack Query. Drizzle + better-sqlite3 и Zod используются в слое хранения; TanStack Virtual ограничивает DOM журнала; Recharts отображает аналитические диаграммы. Все прямые версии точные, полный граф зависимостей хранится в `package-lock.json`.

- `src/app` — серверные страницы, layout, тема и стили.
- `src/shared` — браузерные провайдеры и UI; серверные импорты запрещены ESLint.
- `src/server/config` — env-схема и lazy accessor под `server-only`; значения не передаются клиенту.
- `src/server/db`, `src/server/events` — схема, соединение, миграции, обслуживание, нормализованная запись и поиск.
- `drizzle` — SQL-миграции и metadata Drizzle; FTS/триггеры и STRICT внесены в SQL явно.
- `scripts` — проверка Node, запуск, обслуживание БД и упаковка standalone.
- `tests/unit`, `tests/integration`, `tests/e2e` — автоматические проверки.
- `docs/plans` — решения и отчёт этапов; `docs/design` — согласованные макеты и токены.

Семантические CSS-переменные перенесены из `docs/design/tokens.json`. Golos Text поставляется из локального npm-пакета Fontsource, с кириллицей и лицензией SIL OFL 1.1; копия лицензии — `docs/licenses/Golos-Text-OFL.txt`. Сборка и браузер не обращаются к Google Fonts. Тема применяется ранним скриптом next-themes, сохраняется в localStorage и синхронизируется между вкладками. Production CSP с nonce будет согласована на этапе production-настройки; текущий этап строгую CSP не устанавливает.

Узкие npm overrides: `@esbuild-kit/core-utils → esbuild@0.25.12` (передан из этапа 01) и `@typescript-eslint/typescript-estree` / `eslint` / `@eslint/config-array → minimatch@11.0.1` ([GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249)). После overrides обязательны чистая установка и проверки, а не `npm audit fix --force`. ESLint 10 поддерживается установленным Next.js; npm предупреждает о peer ranges старых React/import/a11y plugins, ещё не включающих 10 ([примечание Next.js](https://nextjs.org/docs/app/api-reference/config/eslint)). Чистая установка и фактический lint проверяются с этим сочетанием. Drizzle Kit пока использует deprecated esbuild-kit; замена его внутренних инструментов здесь не выполняется.
